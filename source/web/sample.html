Well-Architected review

Operational Excellence

  • No CI/CD pipeline described for Lambda deployments — updates appear to be applied manually.
  • No documented rollback strategy for a failed Step Functions execution.
  • Lambda functions don't share a structured (JSON) logging format, which limits CloudWatch Logs Insights queries.
AWS Well-Architected — Operational Excellence Pillar →

Security

  • A single broad IAM role is reused across 14 Lambda functions instead of least-privilege, per-function roles.
  • No AWS WAF sits in front of the public REST API or the CloudFront distribution.
  • Customer-managed KMS keys aren't specified — S3 and DynamoDB appear to rely on default AWS-managed keys.
AWS Well-Architected — Security Pillar →

Reliability

  • No dead-letter queues configured on EventBridge or SQS targets in the order-fulfillment path.
  • DynamoDB tables have no documented backup or point-in-time-recovery strategy.
  • Single-region deployment with no documented failover or DR plan for the order-fulfillment workflow.
AWS Well-Architected — Reliability Pillar →

Performance Efficiency

  • DynamoDB on-demand mode was chosen without a documented access-pattern analysis.
  • No caching layer (API Gateway caching or DAX) sits in front of high-read endpoints like order-status lookups.
  • Lambda memory sizes aren't documented, so cost/performance tuning can't be verified.
AWS Well-Architected — Performance Efficiency Pillar →

Cost Optimization

  • CloudWatch Logs retention is left at the default "Never Expire," accumulating unbounded storage cost.
  • No use of AWS Compute Optimizer or Lambda Power Tuning to right-size function memory.
  • On-demand DynamoDB pricing wasn't compared against provisioned + auto scaling at this order volume.
AWS Well-Architected — Cost Optimization Pillar →

Sustainability

  • No log or data retention limits are documented, increasing the storage footprint unnecessarily.
  • Lambda functions weren't evaluated for arm64 (Graviton2) compatibility, which typically improves performance-per-watt.
  • No S3 lifecycle policy is documented for shipment documents to move them to lower-carbon storage tiers.

How this is built

AWS SOW Validator runs a two-tier review. Tier 1 is fully deterministic — it runs the moment a document is dropped, with no model call, no network round trip beyond loading the page, and no cost. Tier 2 adds an agent-assisted review, powered by Amazon Nova on Amazon Bedrock AgentCore Runtime, for teams that want a deeper, model-informed pass — this report is an example of Tier 2 output.

In Tier 2 the model's job is narrow by design: it reads the SOW and proposes what it sees. Every number in the report — cost lines, arithmetic deltas, severity counts — is computed by Python, not the model. Every integration verdict (native, glue-required, anti-pattern, unverified) is decided by a rule pack against a fixed service graph. Every citation is a real AWS documentation URL resolved by code, never invented text. The model proposes; the pipeline decides.

Request path, every review: CloudFront + WAF + S3 (static site) → Cognito (authentication) → Lambda (API + rule packs) → Bedrock AgentCore Runtime → Amazon Nova on Bedrock → DynamoDB (results, quotas). AgentCore Gateway, Memory, Identity, Policy Engine, Code Interpreter and Bedrock Knowledge Bases are provisioned and reachable in the same deployment, but a standard review invokes none of them — see below for what turns each one on.

Deploy in your AWS account

Access to the hosted instance is limited — sign-up is restricted and the free tier caps out at one full agent review per account. AWS SOW Validator is open source: clone the repository and deploy your own copy into your own AWS account, with no sign-up restriction and no quota. Point it at your own SOW and get this same review — findings, Well-Architected breakdown, cost table, and integration check — against your real design.
